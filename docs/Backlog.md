## Fix: datetime — создание в Python и формат вывода

**Статус:** open
**GitHub:** #84
**Приоритет:** P2
**Категория:** Data / UI

### Проблема

Даты создаются в SQL через `datetime('now')` (формат `YYYY-MM-DD HH:MM:SS`) и так же показываются в шаблонах. Нужен единый Python-источник времени и человекочитаемый вывод `дд.мм.гггг чч:мм`.

### Acceptance criteria

- Создание / обновление `created_at` / `updated_at` задаётся из Python (UTC), а не через SQL `datetime('now')` в DEFAULT и в UPDATE.
- В UI даты отображаются как `дд.мм.гггг чч:мм` (например `01.08.2026 07:48`).
- Формат хранения в SQLite остаётся согласованным и sortable (UTC TEXT); шаблоны не парсят «вручную» разрозненно — общий хелпер/фильтр.
- Unit-тесты на хелпер формата (и при необходимости на запись timestamp из Python).

### Подзадачи

- [ ] Хелпер «сейчас UTC» + запись `created_at` / `updated_at` из Python (posts, comments, users, schema DEFAULT / миграция при необходимости)
- [ ] Jinja-фильтр или хелпер вывода `дд.мм.гггг чч:мм` во всех шаблонах с датами
- [ ] Unit-тесты
- [ ] Кратко обновить DEVELOPMENT / ARCHITECTURE при смене контракта дат

## Auth: rate limit / backoff на login

**Статус:** open
**GitHub:** #56
**Приоритет:** P1
**Категория:** Auth / Abuse prevention

### Проблема

`/auth/login` не ограничен — возможен brute-force по паролю.

### Acceptance criteria

- При серии неудачных попыток с одного IP (и/или login) включается задержка или временная блокировка.
- Успешный login сбрасывает счётчик для субъекта.
- Поведение задокументировано в DEVELOPMENT / ARCHITECTURE (кратко).

### Подзадачи

- [ ] Выбрать механизм (in-memory / SQLite bucket — без новой СУБД)
- [ ] Применить к login POST
- [ ] Unit-тесты на порог и сброс
